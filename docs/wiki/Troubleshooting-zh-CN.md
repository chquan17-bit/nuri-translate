# 故障排查

**从用户看到的现象入手，按接收、队列、worker、模型的顺序缩小范围。**

## 按症状检查

| 症状 | 优先检查 | 处理方式 |
|---|---|---|
| 长时间未使用后提示“应用未响应” | ingress 就绪状态与冷启动延迟 | 实例就绪后再发起一次新请求 |
| 一直显示处理中 | worker 就绪状态、任务投递、完成事件 | 先确认模型是否已被调用，避免反复执行 |
| 卡片只显示提及信息，或提示没有正文 | 所选消息是否含真实文本 | 选择有正文的原始消息，或通过 `/nuri` 输入 |
| 提示输入过长 | 正文与卡片文本的总长度 | 拆成不超过 3,000 字符的段落 |
| 达到每日限额 | KST 日期与已预约次数 | 等待下一个 KST 日期 |
| 提示其他请求正在处理 | 正常执行中的任务或残留全局租约 | 等待完成；异常退出时检查最长 300 秒的租约 |
| Google 429 | 模型 API 限额 | 等待后由用户决定是否重新请求 |
| Google 401 / 403 | Secret Manager 引用与 API 项目权限 | 不暴露值，只检查引用、有效版本和访问权限 |
| Google 5xx / 超时 | 服务提供方或连接问题 | 确认状态后使用较短文本手动重试 |
| 练习按钮过期 | 10 分钟有效期 | 重新运行 Nuri 获取新按钮 |
| 部署后启动失败 | 必需的环境变量和 secret 引用 | 对比 `startup_configuration_invalid` 与先前正常配置 |

## 检查冷启动失败

1. 确认最新 revision 为 `Ready=True`。
2. 确认 ingress `/health` 可访问。
3. 检查上一请求是否出现 `command_accepted`。
4. 确认 worker 是否已经完成处理，再发起一次新的 Discord 请求。

健康检查后立即成功，只能证明已准备好的实例能够运行，不能作为空闲后首次请求问题已经解决的证据。

## 401、403、404 何时属于正常结果

| 请求 | 正常结果 | 原因 |
|---|---|---|
| 无签名的 ingress `/interactions` | 401 | Discord 签名验证 |
| 匿名 worker `/tasks` | 403 | Cloud Run IAM 访问边界 |
| ingress `/tasks` | 404 | ingress 不注册任务处理路由 |

不要因为这些预期结果而取消认证或公开 worker。

## 出错后的用量计数

模型调用前已预约的请求，即使失败也计入每日次数。同一 interaction 再次投递时，如果已预约，就不会再调用模型。不要因未收到响应而删除用量记录或撤销预约。

## 保存诊断信息

记录版本、commit、revision、发生时间、HTTP 状态和固定事件名称。不要附上原文、译文、响应令牌、API 密钥或 HTTP 请求正文。个人截图不应提交至 Git 或 Wiki。
