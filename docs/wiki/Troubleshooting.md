# 문제 해결

**사용자에게 보인 증상에서 시작해 수신, 대기열, worker, 모델 단계 순서로 좁혀 갑니다.**

## 증상별 확인

| 증상 | 우선 확인 | 대응 |
|---|---|---|
| 오랫동안 쓰지 않은 뒤 “앱이 응답하지 않음” | ingress 준비 상태와 첫 기동 지연 | 인스턴스가 준비된 뒤 새 요청을 한 번 실행 |
| 처리 중 표시만 남음 | worker 준비 상태, 대기열 전달, 완료 이벤트 | 모델 호출 여부부터 확인하고 반복 실행 자제 |
| 카드가 아닌 멘션만 보이거나 본문 없음 안내 | 선택한 메시지의 실제 텍스트 | 텍스트가 있는 원본 메시지 선택 또는 `/nuri` 입력 |
| 글이 너무 길다는 안내 | 본문과 카드 텍스트의 합산 길이 | 문단을 나누어 3,000자 이내로 입력 |
| 오늘 한도 도달 | KST 날짜와 예약된 시도 횟수 | 다음 KST 날짜까지 대기 |
| 다른 요청 처리 중 | 정상 실행 또는 남은 전역 lease | 처리 완료를 기다림. 비정상 종료면 최대 300초 lease 확인 |
| Google 429 | 모델 API 한도 | 시간을 둔 뒤 사용자 판단으로 재요청 |
| Google 401 / 403 | Secret Manager 참조와 API 프로젝트 권한 | 값 노출 없이 참조·활성 버전·접근 상태 확인 |
| Google 5xx / 시간 초과 | 공급자 또는 연결 오류 | 상태 확인 후 짧은 문장으로 수동 재시도 |
| 연습 버튼 만료 | 10분 유효 시간 | Nuri를 새로 실행해 버튼 재발급 |
| 배포 후 시작 실패 | 필수 env와 secret 참조 | `startup_configuration_invalid`와 이전 정상 설정 비교 |

## 첫 기동 실패를 확인하는 순서

1. 최신 revision이 `Ready=True`인지 확인합니다.
2. ingress `/health`에 접근 가능한지 확인합니다.
3. 이전 요청에 `command_accepted`가 있었는지 확인합니다.
4. worker의 처리 완료 여부를 확인한 뒤 새 Discord 요청을 한 번 실행합니다.

건강 상태 확인 직후의 성공은 이미 준비된 인스턴스에서의 성공입니다. 이를 유휴 뒤 첫 요청 문제가 해결된 근거로 사용하지 않습니다.

## 401, 403, 404가 정상인 경우

| 요청 | 정상 결과 | 이유 |
|---|---|---|
| 서명 없는 ingress `/interactions` | 401 | Discord 서명 검증 |
| 익명 worker `/tasks` | 403 | Cloud Run IAM 경계 |
| ingress `/tasks` | 404 | ingress에는 작업 처리 라우트 없음 |

이 결과를 오류로 보고 인증을 해제하거나 worker를 공개하지 않습니다.

## 처리 중 오류 뒤의 횟수

모델 호출 전에 예약된 요청은 실패하더라도 일일 횟수에 포함됩니다. 동일 interaction을 다시 전달해도 이미 예약되어 있으면 모델을 호출하지 않습니다. 응답을 받지 못했다고 사용량 기록을 지우거나 예약을 취소하지 않습니다.
